# Architecture Decisions

## Approved contracts

1. **Modular monolith.** Keep transport (`app/api`), application services, domain/rules,
   workflow engine, infrastructure/persistence, and retry worker behind clear package
   boundaries. Do not split into services for the MVP.
2. **FastAPI is the interface.** Swagger UI is generated by FastAPI; no React frontend.
3. **SQLite is the durable MVP store.** SQLAlchemy 2.x models/repositories own persistence.
4. **YAML is declarative input, never executable code.** Rules use an allowlisted operator
   set; never use `eval()` or `exec()`. Validate types and all graph references before
   activation.
5. **Immutable config versions.** Activation creates/selects a version; never edit a prior
   committed version to express a rule change. In-flight requests retain their starting
   version.
6. **Idempotency is database-enforced.** Unique scope is `(workflow_id, idempotency_key)`;
   persist canonical request hash. Matching replay returns prior request, mismatched replay
   conflicts.
7. **Audit and state are atomic.** Each workflow transition and its audit event commit in one
   transaction. External calls happen outside database transactions and use stable operation
   keys.
8. **Retries are durable and bounded.** Persist due time, attempt count and outcome in
   SQLite. MVP worker is single-process/single-worker; document crash/replay limitations.
9. **Determinism and explanation.** Rule evaluation is pure and emits ordered traces with
   observed/expected values, result, reason and configuration version.

## Phase 1 choices

- Python package metadata uses PEP 621 in `pyproject.toml`, setuptools build backend.
- SQLite default and config directory are documented in `.env.example`; settings are not
  yet loaded by application code.
- Alembic is deferred unless later schema needs justify it within the deadline.

## Phase 2 choices

- Workflow YAML transitions are explicit triples (`from_stage`, `outcome`, `to_stage`) and
  are checked against the source stage type. Each workflow must contain exactly one terminal
  stage for each of `APPROVED`, `REJECTED`, and `MANUAL_REVIEW`.
- All graph cycles are rejected in the MVP. Every stage must be reachable from the entry,
  every nonterminal stage must have an outgoing transition, and terminal stages have none.
- Config models are frozen Pydantic v2 models with tuple collections; bulk loader results are
  read-only and keyed by `(workflow_id, version)`. A rule change creates a new version.
- Groups evaluate every child for complete trace output. Rules retain declaration order;
  when several fail, REJECT takes precedence over MANUAL_REVIEW.
- Missing ordinary comparison fields produce explicit failed traces and follow that rule's
  configured failure action. `exists` handles optional presence explicitly. Incompatible
  comparison types raise `RuleEvaluationError` to prevent silent coercion or decisions.

## Phase 3 choices

- SQLAlchemy metadata creates the initial schema at app startup; Alembic remains deferred.
- SQLite foreign keys are enabled per connection. `BEGIN IMMEDIATE` serializes SQLite
  transactions before the idempotency lookup, avoiding deferred lock-upgrade races. The MVP
  assumes one application process; SQLite write throughput is intentionally limited.
- Startup snapshots the exact validated workflow model plus a version-specific structural
  input schema and checksum. Existing `(workflow_id, version)` content is immutable; changed
  content under the same version prevents startup. Initially, highest numeric version is
  selected active; Phase 5 adds a persistent operator selection.
- Canonical idempotency hash covers workflow ID and `data`, not active config version. A
  repeated request after a version change therefore returns the original pinned request.
- Request creation, initial execution (`RECEIVED`) and audit sequence 1 share one transaction.
  Stage execution is intentionally deferred. New intake returns 202; matching replay returns
  200 with `Idempotency-Replayed: true`; payload mismatch returns 409.
- Requests have a composite foreign key to the persisted `(workflow_id, config_version)`
  snapshot, enforcing version pin integrity at the database boundary.
- Input shape/type requirements live in per-version `configs/input_schemas` YAML sidecars;
  eligibility thresholds remain only in the workflow rule configuration.

## Phase 4 choices

- Intake remains storage-only. Execution is an explicit `POST /api/v1/requests/{id}/execute`
  trigger. Repeated calls return the current state; the database lease/state check prevents
  concurrent claims and final outcomes do not create duplicate decisions.
- Request and execution `status` are canonical and updated in the same transaction. Legal
  edges are RECEIVED->PROCESSING, PROCESSING->APPROVED/REJECTED/MANUAL_REVIEW/RETRY_WAIT/FAILED,
  RETRY_WAIT->PROCESSING/FAILED, and (Phase 5) authorized MANUAL_REVIEW->APPROVED/REJECTED.
- Each stage movement and state transition writes an ordered audit event atomically. Rule
  traces and external result categories are kept in execution context and copied into the
  terminal/holding Decision explanation with the pinned config version.
- Provider behavior is behind a typed adapter interface. The deterministic simulator reads
  only server configuration, not request fields. Unexpected provider exceptions are
  retryable technical failures and follow bounded retry/fallback behavior.
- `max_attempts` counts the initial external call. Delay after failed attempt n is
  `min(max_delay, base_delay * 2^(n-1))`. Defaults and lease duration are environment-configurable.
- External calls happen with no SQLAlchemy session/transaction open. A stable operation key
  is derived from workflow/version/request/stage/operation. Retrying after a crash can repeat
  the call; provider-side idempotency is required for side-effect deduplication.
- Retry jobs and execution claims have durable expiry leases. One retry worker process is
  supported. The one-shot worker reclaims expired claims; there is no heartbeat or distributed
  exactly-once guarantee.
- SQLite transactions use `BEGIN IMMEDIATE`; simple additive SQLite upgrades preserve Phase 3
  data while adding execution context and retry claim columns. Alembic remains deferred.

## Phase 5 decisions

- Startup inserts validated newly discovered workflow snapshots as inactive. It initializes
  the highest version only when no active row exists, then preserves that selection on
  restart. Intake uses the active row; request pins remain unchanged after activation.
- Activation verifies the persisted snapshot checksum, workflow graph and input schema, then
  switches the active row and appends an `AdminAuditEvent` in one transaction. The partial
  unique index enforces at most one active version per workflow. Re-activating the current
  version is a no-op without a duplicate admin audit event.
- Audit reads return actual rows in sequence order. Config version comes from the pinned
  request; stage can be null when a persisted historical event had no stage reference.
  Explanations read persisted traces/results and never re-evaluate old decisions.
- Review queue reads and privileged writes require environment-configured `X-Admin-Token`.
  The demo token maps to fixed actor `demo-admin`; reviewer identity is never accepted from
  a client. Review reason/action, request/execution status, held Decision update and
  `REVIEW_RESOLVED` event commit atomically. Same action/reason is idempotent; conflicts
  return 409. SQLite `BEGIN IMMEDIATE` serializes competing actions.
- Review queue reads use the same admin credential because they reveal pending case references.
  Audit/explanation reads remain request-scoped demo endpoints and never return the whole
  input payload. Admin auth is not production user identity or role-based access control.
  Missing server configuration returns 503; missing/invalid credentials return 401/403.
  Token values are not logged or echoed.

## Phase 6 audit conclusions

- The Phase 6 audit found no confirmed business-logic defect requiring runtime changes.
  Added tests close evidence gaps for missing/wrong/unconfigured admin credentials, review
  and activation commit rollback, newly discovered inactive config versions, and repeated
  execution after a final outcome.
- Existing Phase 3-5 tests already cover invalid input schema, idempotency mismatch/replay,
  concurrent intake, provider errors/timeouts, retry recovery/exhaustion, worker restart,
  immutable pins, review conflicts/concurrency, and audit/decision consistency.
- Confirmed limitation: provider calls remain at-least-once across a crash after external
  success but before local commit. Leases, stable operation keys and local transactions do
  not create distributed exactly-once behavior.
